Experiments

Smaller builds and frameworks. Some worked. Some are still hypotheses, and say so.

01

A reusable experimentation framework

A framework covering hypothesis definition, primary and secondary metrics, guardrail metrics, experiment design, statistical significance and decision criteria, written once so that each new test does not restart the argument about what counts as success.

I applied it to product flows across acquisition, activation, engagement and conversion, connecting quantitative signals to qualitative user feedback.

Why it exists

The decision criteria have to be written before the result arrives. Otherwise the result writes them.

  1. Problem

    Teams re-litigate what success means after every test, which is when motivated reasoning is strongest.

  2. Hypothesis

    Fixing the decision rule up front makes results faster to act on and harder to argue with.

  3. Result

    Applied across Hanglet’s funnel work, where it set the success threshold and the guardrail before each experiment rather than after the result arrived.

02

Agent workflow automation

Multi-step AI workflows that break an enterprise task into specialised agent capabilities: structured retrieval, summarisation, contextual reasoning and action generation. using LLM orchestration, prompt engineering, structured outputs and explicit evaluation criteria.

The interesting constraint is not model quality. It is that a workflow with four agents has four places to be confidently wrong, so the evaluation criteria have to sit between the steps rather than only at the end.

Shipped version

The same pattern in production at Deloitte: four agents in one workflow, cutting manual case-resolution effort by 80%.

  1. Problem

    Operational tasks are too varied for a single prompt and too repetitive to keep doing by hand.

  2. Hypothesis

    Decomposing into narrow agents with structured outputs beats one general agent on consistency.

  3. Result

    Validated in the enterprise case: 80% reduction in manual case-resolution effort across four agents (Case Summarizer, Context Reader, Case Updater, Resolution Plan Generator).

03

Guided setup as an adoption lever

At Work4Flow I designed and implemented a guided setup experience to simplify onboarding, configuration and adoption of a platform application. Enterprise software usually treats configuration as an implementation problem; treating it as an onboarding problem changes who has to be in the room.

Status

Shipped. Adoption impact not measured. Not yet validated.

  1. Problem

    Configuration complexity delays time-to-value and pushes every new deployment through a specialist.

  2. Hypothesis

    A guided path through setup reduces dependence on that specialist and shortens time-to-first-use.

  3. Result

    Not yet validated. I would measure setup completion rate and time-to-first-configured-instance against the previous path.

04

Data-driven UI variants

Nine or more dynamic UI variants built in UI Builder, driven by product metrics and client-state parameters rather than by static configuration, with backend capabilities behind them surfacing real-time platform data.

The product argument: if the interface can respond to the state a client is actually in, the same application can serve very different maturity levels without forking.

Status

Shipped. Comparative impact not yet validated.

05

Agents that automate my own ServiceNow work

I play with AI agents that take over parts of my own ServiceNow work, built on the platform’s own agent tooling. Triage, pulling context together, summarising a case, drafting the next step. The repetitive middle of the job rather than the judgement at either end of it.

The reason this sits on a product portfolio rather than in a scratch folder is that I am the user. The feedback loop is same day. There is nobody to interview and no research to commission, and I find out immediately when the thing I built is annoying to use.

Most product problems are harder than this one. It is still the fastest way I know to practise the actual loop: notice a friction, decide whether it is worth automating, build the smallest version, then live with the result.

Status

Ongoing. Personal tooling rather than a shipped product, so the only honest measure is whether I am still using it a month later.

  1. Problem

    Platform work is full of tasks that are repetitive without being identical, which is exactly the shape that resists scripting.

  2. Hypothesis

    A narrow agent with a structured output absorbs the variation a script cannot, on tasks small enough that I can still check the answer by hand.

  3. Learning

    The agent is rarely the hard part. Deciding which tasks are safe to hand over, and how I would notice if one started being confidently wrong, is the hard part.
